# 产品分析：为什么现有 Redis 客户端让人难受

> 本文是 Rill v0.1 的产品判断记录。结论先行：**痛点主要不在「功能少」，而在「加载策略、交互模型和生产安全感」三件事上。**

---

## 1. 目标用户与场景

Rill 面向的不是偶尔打开 Redis 看一眼的人，而是每天要在多个环境之间切换的开发者 / SRE / 后端工程师：

- 同时维护 5–50 个 Redis 实例，开发、预发、生产混在一起
- 经常需要定位一个 Key、改一个 Hash 字段、看 TTL、查慢查询
- 生产环境操作必须克制，最好有「只读」这把锁
- 习惯键盘，讨厌为了一次查询点五层菜单
- 用 MacBook，外接显示器，长时间开着客户端

这些用户的共同诉求可以概括为三个词：**快、稳、敢用**。

---

## 2. 现有客户端的拆解

| 客户端 | 优势 | 真实短板 |
| --- | --- | --- |
| **RedisInsight**（官方） | 功能最全、Cluster/模块支持好、有 CLI 和 profiler | Electron 体积大、冷启动慢、内存高；信息架构偏「平台」，打开一个 Key 的路径长；默认体验偏重 |
| **Another Redis Desktop Manager** | 轻量、开源、连接管理和树视图成熟 | 仍是 Electron；大树/大集合下滚动与渲染会抖；类型编辑能力有限；界面密度高、视觉偏旧 |
| **Medis** | 视觉克制、上手快 | 功能面窄，复杂类型与运维能力弱；更新节奏慢；连接方式与生产安全能力不足 |
| **TablePlus** | 统一数据库工作台、原生质感好 | Redis 只是附属能力：无命名空间树、无慢日志/订阅、类型编辑基础；付费 |
| **redis-cli** | 最快、最可靠、脚本友好 | 没有可视化；大结果集阅读困难；不适合日常改数据 |

### 共性问题的根因

#### ① 加载策略：用「数据库浏览器」的思路做 KV

关系型数据库有表结构，可以分页；Redis 没有 schema。很多客户端于是选择了最朴素的做法：

```text
连接成功 → KEYS * → 渲染全部
```

在 10 万 Key 的实例上，这一条就能让 Redis 的 `latency` 抖动、让客户端主线程卡死，甚至触发内存峰值。正确做法只有一个：**SCAN 游标 + 增量渲染**，并且接受「键空间是流式的，不是一张表」。

#### ② 渲染策略：把 10 万个 DOM 节点交给浏览器

即使后端用了 SCAN，把结果一次性塞进列表也会卡。虚拟滚动不是「优化项」，而是这类工具的地基。

#### ③ 交互模型：所有动作都围绕「弹窗」

连接、选库、看值、改值、设 TTL、删 Key 各自一个弹窗，流程被打断。高频操作应该**就地完成**：行内编辑、TTL 胶囊、右键菜单、命令面板。

#### ④ 生产安全感：工具默认「你能操作一切」

- 密码明文存在 JSON 里
- 没有只读模式，误触即写
- `FLUSHALL` 和 `GET` 一样只需回车
- 生产和测试连接长得一模一样

这不是功能问题，是**信任问题**。一旦用户在生产上误删过一次 Key，他就会回到 `redis-cli`。

#### ⑤ 连接能力：企业网络里的真实形状

真实环境里 Redis 很少直接暴露：

- 只允许通过 SSH 跳板机访问
- 开了 TLS，甚至是自签名证书
- 用 ACL 用户名而不是 default
- 一个实例 16 个 DB

这些能力在不少客户端里是「有，但不好用」，或者干脆缺失。

#### ⑥ 性能观感：Electron 的原罪被放大了

Electron 本身不是不能用，但「Electron + 全量渲染 + 同步 IPC + 大对象序列化」的组合会让每一次点击都变慢。用户感知到的不是 200 MB 内存，而是**输入延迟**和**窗口切换时的顿挫**。

---

## 3. Rill 的产品原则

1. **永远不调用 `KEYS`。** 只用 SCAN；稀疏匹配时后端自动多扫几轮，避免第一页空白。
2. **UI 线程不做 I/O。** 所有 Redis 操作在 Rust 异步运行时里完成，前端只消费结果。
3. **默认只读是美德。** 生产连接建议开启只读保护；危险命令必须二次确认。
4. **就地操作优先。** 行内编辑、TTL 胶囊、右键菜单，减少弹窗层级。
5. **键盘是一等公民。** ⌘K 能到任何地方；↑↓ 选 Key；⌘S 保存。
6. **不假装拥有全部数据。** 键空间是流式的；树只聚合「已加载」的 Key，并明确告诉用户。
7. **视觉为信息密度服务。** 深色优先、低饱和背景、等宽数字、类型色只做点缀。

## 4. 功能取舍

### 必须做（v0.1 已实现）

- 连接管理：TLS、SSH 隧道、ACL、DB、只读
- 键空间：SCAN、模糊搜索、类型过滤、虚拟列表、命名空间树、数据库自由切换
- 类型化查看/编辑：String、Hash、List、Set、ZSet、Stream
- TTL / 重命名 / 删除 / 新建
- 控制台 + 历史 + 危险命令确认
- 概览、INFO、慢日志、客户端列表
- 发布订阅、空间分析
- 命令面板、双主题

### 故意不做（v0.1）

| 功能 | 原因 |
| --- | --- |
| Cluster / Sentinel | 跨节点 SCAN、slot 路由、故障转移会显著抬高 v0.1 复杂度；先把单机体验做到最好 |
| MONITOR | 阻塞式连接与多路复用冲突；需要独立裸 RESP 流与背压设计 |
| 全库大 Key 扫描 | 成本高、容易误伤生产；先用抽样分析 + 明确上限 |
| 云端同步 / 团队协作 | 与「本地、无账号、无遥测」的定位冲突 |
| 通用 SQL 工作台 | 聚焦 Redis，避免变成四不像 |

### 关键指标

- 冷启动 < 1.5 s，安装包 < 20 MB
- 10 万 Key 列表滚动 ≥ 55 fps
- 单页 SCAN（200 Key）端到端 < 300 ms（局域网）
- 常驻内存 < 150 MB（单窗口）
- 危险操作误触率 = 0（只读 + 确认双保险）

## 5. 技术选型

### Tauri 2 vs Electron

选择 Tauri 的核心理由不是「包小」，而是：

- Rust 后端天然适合做连接池、超时、流式 SCAN、二进制安全处理
- 系统 WKWebView 让滚动和文本渲染更接近原生
- 13 MB 的安装包让「随手打开」成为可能

代价是：WKWebView 的调试体验不如 Chromium、跨平台一致性需要额外验证。对 macOS 单平台 v0.1 来说，这个交换是值得的。

### SCAN 而不是 KEYS

- `SCAN` 的语义是「可能重复、可能为空、最终覆盖」，必须在 UI 层接受这一点
- 后端对空批次做有限重试（最多 8 轮），避免用户第一眼看到空列表
- 前端只在滚动到底部时继续，绝不后台全量拉取

### Rust 侧 MultiplexedConnection

- 一条 TCP 连接复用所有命令，减少握手成本
- 阻塞类命令（`BLPOP`、`MONITOR`）会占住连接，因此禁用或走独立通道
- 每个操作有 25–30 秒超时，避免 UI 永久 pending

### 密码放 Keychain，而不是加密 JSON

- 加密 JSON 需要管理密钥，最终还是要落在某处
- macOS Keychain 是系统级、可审计、用户熟悉的位置
- 缺点：每次读取会 spawn `security` 进程；未来可以换成原生 Security.framework

### SSH 用系统 `ssh -L`，而不是内置 SSH 库

- 复用用户的 `~/.ssh/config`、agent、known_hosts
- 少一个重量级依赖，行为与用户平时登录一致
- 限制：仅支持密钥 / agent，不支持交互式密码

## 6. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| SCAN 在大库上仍可能慢 | 分页 + 游标 + 超时；不做后台全量扫描 |
| 用户在只读模式外误操作 | 删除/重命名/危险命令全部二次确认 |
| Keychain 读取弹窗 | 仅在真正连接时读取；启动不预取 |
| SSH 隧道泄漏进程 | `Tunnel` 的 `Drop` 中 kill；断开连接即销毁 |
| TLS 自签名证书 | 提供「跳过校验」开关 + 显式警告，不静默降级 |
| 大 String 撑爆内存 | 512 KB 截断 + 编辑锁定 |
| 二进制 Key/Value | 有损展示 + 二进制标记；编辑禁用，避免误写 |

---

## 7. 结论

Rill 不试图成为「Redis 的 IDE」。它要解决的是一个更具体的问题：

> 让一个每天在多个 Redis 环境里工作的人，**用最少的点击和等待**，安全地看到并修改他想看的那条数据。

v0.1 把单机体验、键空间性能、类型化编辑和生产安全做扎实；Cluster、MONITOR、模块类型留给后续版本。这个顺序比「功能列表更长」更重要。
